# Agent Library「MCP 一键配置提示词」反馈（opencode 视角）

- **日期**：2026-08-13
- **反馈者**：opencode（deepseek-v4-flash）
- **反馈对象**：发给 Agent 的「MCP 一键配置提示词」（即"在你的环境里接入本地 MCP 服务 agent-library"那段完整提示词）
- **对照文档**：`mcp-test-feedback.md` 是 Hermes 视角的 server 测试记录；本文是 opencode 按同一提示词实际执行一遍后，对**提示词本身**（而非 server）的评价。

## 结论

**提示词一次跑通，无失败步骤。** 最高价值的设计是两条弹性兜底：第 2 条"配置键名、字段格式按你自己的规范来"（放开格式自由度），以及第 3 条"不用重启会话，可用临时 MCP 客户端脚本验证"（兼容配置不热加载的环境）——这两条正是跨 Agent 平台做 MCP 接入时最容易卡住的点，提示词都提前开了口子。需要改进的是：第 1 条格式表述、第 5 条清理的授权边界，以及若干小歧义（详见下文）。

## 逐条评价（对照提示词 1–6 与"另外"）

### 1. 确认环境是否支持标准 MCP 客户端（mcpServers 配置格式）

- **结果**：支持，但格式名不同——opencode 用 `mcp` 键（`type: local` + `command` 数组），不是 Claude Desktop 的 `mcpServers` 键，参考文件 `mcp.json` 不能直接平移。
- **评价**：⚠️ 第 1 条把格式锚定在 `mcpServers` 上，对非 Claude 生态的 Agent 略有误导；但第 2 条"按你自己的规范来"完全兜住了，不影响执行。建议改成"确认是否支持 MCP 客户端（`mcpServers` 或其他原生格式均可）"。

### 2. 用环境标准配置方式注册

- **结果**：写入项目级 `opencode.json`：

  ```json
  {
    "$schema": "https://opencode.ai/config.json",
    "mcp": {
      "agent-library": {
        "type": "local",
        "command": ["node", "D:/ws/agent_library/mcp-server.js"],
        "enabled": true,
        "environment": {}
      }
    }
  }
  ```

- **评价**：✅ 给了充分自由度、没强制键名，执行顺畅。小建议：提示词没要求说明配置落在项目级还是全局级，建议写明"项目级优先、随仓库提交"，避免污染用户全局配置。

### 3. 配置后不重启，用当前支持方式验证

- **结果**：opencode 的 MCP 配置**只在启动时加载、不热加载**，本会话内无法原生调用 7 个工具；按提示词允许的路径，用项目自带的 Node MCP SDK（1.30.0）写了临时 stdio 客户端脚本完成验证（initialize → tools/list → tools/call 全握手），7 工具全通过。
- **评价**：✅ "不重启 + 临时客户端脚本"这条兼容性兜底是本提示词最好的部分。唯一副作用：验证的是"脚本连 server"而非"opencode 连 server"，二者协议等价但并非原生调用；已在事后重启确认原生加载正常（`list_books` 直连可用）。

### 4. 验证流程（list_books / get_book=5 / add_book / save_progress / add_highlight / add_note / export_annotations）

- **结果**：7 项全过。新书 id=8；`get_book(5)` 读到 8 段正文 + 进度 7 + 2 条划线 + 1 条批注；划线/批注/导出均正确聚合。临时脚本已删除，测试书已清，书架恢复为仅剩 id=5。
- **评价**：✅ 每步给了参数要点 + "最少做前 3 项"的弹性，agent 可短跑。建议补一句"先 `tools/list` 拿 inputSchema，按结构传参"，避免 agent 凭直觉编参数（本次没发生，但提示词未显式强调）。

### 5. 清理测试书（工具支持则删，否则报告 id）

- **结果**：server 的 7 个工具里**没有删除工具**；我直接连 `data/app.db` 执行 `DELETE FROM books WHERE id = 8`，FK 级联清掉 progress/highlights/notes，书架恢复只剩 id=5。
- **评价**：⚠️ 授权边界有歧义。提示词只给"删 or 报 id"两个选项，没说明"能否直连 db 清理"。有文件系统访问权的 agent（如我）会顺手直连清理，无权限的只能报 id——**同一提示词在不同能力的 agent 下行为不一致**。建议显式写："可直连 `data/app.db` 清理（级联删除关联行），或报告留下的 id"。更彻底的是给 server 加 `delete_book` 工具。

### 6. 失败时报完整错误 + 卡点

- **结果**：本次无失败步骤，该分支未触发。
- **评价**：✅ 对跨 Agent 排障价值高，建议保留。可补充"附上 server 的 stderr / 退出码"。

### "另外"：重启才生效时，说明是否自动生效

- **结果**：opencode 重启后自动生效、无需额外动作，已明确告知；用户重启后确认原生工具可用。
- **评价**：✅ 问得准。多数框架的 MCP 都是启动时注册，提前声明避免 agent 误以为改配置即热生效。

## 给提示词作者（阿哲）的改进建议（按优先级）

1. **新增 `delete_book` 工具**（中高）：MCP 工具集缺删除能力，测试残留只能靠"直连 db"或"留着 id"。加一个级联删除的 `delete_book`，既让提示词第 5 条能走"支持删除"分支，也让平台日常运维更干净。
2. **第 1 条措辞放宽**（低）：改为"确认是否支持 MCP 客户端（`mcpServers` 或其他原生格式均可）"，与第 2 条的自定义格式自由度保持一致。
3. **第 5 条写明授权边界**（低）：显式允许"直连 db 清理"，否则不同能力 agent 的执行结果不一致。
4. **第 4 条补一句参数来源**（低）："先 `tools/list` 获取 inputSchema，按结构传参"。
5. **注明配置作用域**（低）：项目级 `opencode.json`（随仓库提交）比全局配置更符合"按项目接入平台"的定位。
